# 方案定义：六项产出与"是否可行"闸门

## R — Reading (原文)

> 「**价值评估** → 业务价值；**优先级排布** → 影响范围；**目标定义** → 成功指标；
> **流程拆解** → 数据标准；**数据准备** → 风险约束；**方案设计**。→ **是否可行**
> （判断）— 否 → **调整范围**（回环）；是 → 继续。**试点规划** → 时间节奏；
> **资源协同** → 角色分工；**实施计划**。」
> —— 一图讲透 FDE（Simon的数据笔记），方案定义阶段

## I — Interpretation (自述)

方案定义把"值得做的场景"转换成"可开工的方案"。图上的结构是**三组产出 + 一道闸门
+ 三项开工准备**：

1. **六项定义**（核心）：价值评估（对齐业务价值）、优先级排布（明确影响范围）、
   目标定义（翻译成可度量的成功指标）、流程拆解（顺带定数据标准）、数据准备
   （标注风险约束）、方案设计（技术路线收口）。
2. **是否可行闸门**：六项齐了才判。不可行 → **调整范围**回环（缩场景/降目标/
   换路径），不是直接毙掉，也不是硬上。
3. **三项开工准备**：试点规划（时间节奏）、资源协同（角色分工）、实施计划。

这阶段的本质：**把AI项目从"愿景"翻译成"工程"**。成功指标、流程拆解、数据准备
三样是AI项目与一般IT项目差异最大、也最常缺失的部分。

## A1 — Application Example（来源案例或明确标记的演练）

原素材**未提供实际案例**。以下为明确标记的合成演练：

> 演练（合成，按图复算）：场景=智能补货。六项定义：价值评估=缺货成本年约
> RM 2M；优先级=影响 200 家门店，高影响高优先；目标定义=试点店缺货率降 30%；
> 流程拆解=门店申报→区域审核→配送，定义各环节数据标准（SKU/时点/数量）；
> 数据准备=2年销售流水+库存快照，风险约束=促销期数据噪声大；方案设计=时序
> 预测+安全库存规则。可行性判断：数据可得但促销噪声是硬约束 → **不可行→调整
> 范围**：试点缩小到非促销品类，指标改为常规品类缺货率降25%。二判可行→试点
> 规划（8周/2店）、资源协同（数据组+门店运营+算法各1人）、实施计划成文。

## E — Execution (可执行步骤)

**输入契约**：已过"值得做"闸门的场景描述、业务上下文（可拿到的数据源清单、
干系人）。缺场景来源或数据源信息时先询问。

1. **六项定义**（顺序即依赖）：
   a. 价值评估：业务价值量化到币值或核心指标（完成标准：有数或标注"无法量化+理由"）；
   b. 优先级排布：影响范围（用户/流程/收入）成文；
   c. 目标定义：成功指标 = 指标名 + 基线 + 目标值 + 测量方式（完成标准：可判定
      达标与否，不可判定即返工）；
   d. 流程拆解：现流程分步图 + 每步数据标准（字段/粒度/时点）；
   e. 数据准备：数据源清单 + 获取方式 + 质量风险约束；
   f. 方案设计：技术路线一页纸（模型/集成/兜底入口，兜底引用 fde-risk-human-fallback）。
2. **是否可行闸门**：逐项核查 a–f；任一项"不可判定/数据不可得/指标不可测" →
   判不可行，执行**调整范围**回环（缩场景、降指标、换路径），回到 d 重拆，二判。
3. **三项开工准备**：试点规划（范围/时长/节奏）、资源协同（角色分工表）、实施
   计划（里程碑）。
4. **输出契约**：一页式方案定义文档：六项定义各一节 + 闸门判定记录（含回环
   次数与调整内容）+ 三项开工准备表。

## B — Boundary (边界)

- **不要**用于：还在选场景（回 fde-opportunity-discovery）；试点已经在跑、要处理
  执行问题（回 fde-pilot-execution）。
- **失败模式**：目标定义写成"提升效率"（不可判定）；流程拆解跳过（数据标准
  无从谈起）；把可行性判断当走流程（六项缺项硬判可行）。
- **作者盲点**：图未给"是否可行"的判定细则，本卡用"逐项可判定"作操作化标准
  （E段已标注为约定）；图中"调整范围"回环只画到流程拆解，实际可能要动到目标
  甚至价值评估，执行时按需上溯。

## Purpose

方案定义阶段把已过"值得做"闸门的 AI 场景，从"愿景"翻译成"工程"：六项定义（价值评估、优先级排布、目标定义、流程拆解、数据准备、方案设计）齐备并经"是否可行"闸门判定可行后，才产出试点规划、资源协同、实施计划三项开工准备。成功指标、流程拆解、数据准备是 AI 项目与一般 IT 项目差异最大、也最常缺失的部分。

## Instructions

完整可执行步骤见 `## E — Execution`；紧凑步骤列表：

1. 收集输入：已过闸门的场景描述 + 业务上下文（数据源清单、干系人）；缺信息先询问。
2. 按依赖顺序完成六项定义：价值评估（量化到币值或核心指标）→ 优先级排布 → 目标定义（指标名+基线+目标值+测量方式）→ 流程拆解（含每步数据标准）→ 数据准备（清单+获取方式+质量风险约束）→ 方案设计（技术路线一页纸）。
3. 过"是否可行"闸门：逐项核查，任一项不可判定/数据不可得/指标不可测 → 执行"调整范围"回环（缩场景、降指标、换路径）后二判。
4. 三项开工准备：试点规划（范围/时长/节奏）、资源协同（角色分工表）、实施计划（里程碑）。
5. 输出一页式方案定义文档：六项定义各一节 + 闸门判定记录（含回环次数与调整内容）+ 开工准备表。

## Examples

1. 输入："智能补货场景要立项，帮我写方案定义" → 期望：完成六项定义（价值=缺货成本年约 RM 2M、成功指标=试点店缺货率降 30% 等），若促销期数据噪声被判硬约束则触发"调整范围"回环（缩到非促销品类、指标改 25%），二判可行后给出试点规划/资源/实施计划表。
2. 输入："评审这份 AI 项目方案能不能开建" → 期望：逐项对照六项定义核查，缺成功指标基线或数据准备清单即判"不可行"，指出调整路径而非硬上或直接毙掉。
3. 输入："数据团队问到底要什么数据" → 期望：从流程拆解产出每步数据标准（字段/粒度/时点），汇总为数据源清单+获取方式+质量风险约束。

## Limitations

- 只适用于已选定的场景（还在选场景 → 回 fde-opportunity-discovery）；试点已在跑的执行问题 → fde-pilot-execution。
- 来源图未给"是否可行"的判定细则，本卡以"逐项可判定"作操作化标准（约定，E 段已标注）。
- "调整范围"回环图中只画到流程拆解；实际可能要上溯到目标定义甚至价值评估。
- 流程拆解与数据准备的现场作业方法、价值叙事分别见 fde-process-mapping 与 fde-system-outcome，本卡不展开。

## Troubleshooting

- 错误：目标定义写成"提升效率"。原因：指标不可判定。解决：改为"指标名+基线+目标值+测量方式"，不可判定即返工。
- 错误：数据标准无从谈起。原因：跳过了流程拆解。解决：先产出现流程分步图，再定每步数据标准。
- 错误：六项缺项却判"可行"。原因：把可行性判断当走流程。解决：逐项核查后才判，任一项缺项即触发调整范围回环。

## Prerequisites

- 输入契约要求：已过"值得做"闸门的场景描述、业务上下文（可拿到的数据源清单、干系人）——缺时先询问。
- 无外部工具或 API 密钥要求；方案设计中"兜底入口"需引用 fde-risk-human-fallback 卡。
