# 三类回环：问题修正、优化迭代、运营反馈

## R — Reading (原文)

> 「**能力构建** ← 问题修正（反馈回环）… **试点通过？**（判断）— 否 → **优化迭代**
> （回环）… **运营反馈** ← 优化迭代（回环）→ **持续优化**。」
> —— 一图讲透 FDE（Simon的数据笔记），三处回环箭头标注

## I — Interpretation (自述)

图上有三条回环，分别锚在三个时期，**不可混用**：

1. **问题修正**（构建期）：能力构建与联调测试中发现的缺陷，修正后回能力构建。
   短周期、高频、工程性（bug/特征/接口）。
2. **优化迭代**（试点期）：试点未通过后的整体改进——可能动特征、动产品、动
   流程。中周期、以"试点通过"为收敛条件。
3. **运营反馈**（运营期）：规模化上线后，从真实运营数据与用户反馈中持续挖
   改进点，进入持续优化。长周期、永不收敛（这是特性不是缺陷）。

三条回环的**输入源、周期、收敛条件**都不同。最常见的错误是错配：用工程级
"问题修正"去回应业务级"试点不通过"（修了bug但业务还是不买账），或运营期还
想用一轮"优化迭代"解决所有问题。

## A1 — Application Example（来源案例或明确标记的演练）

原素材**未提供实际案例**。以下为明确标记的合成演练：

> 演练（合成，按图复算）：同一系统三个时期——(1) 构建期：接口超时→问题修正
> （改超时+重试），半天级；(2) 试点期：门店不用系统→优化迭代（把"为什么这样
> 建议"解释层加上+采纳流程简化），8周后二轮试点通过；(3) 运营期：月度反馈=
> 促销季误差升高→加入促销特征→下月误差回落。复算：三次改进分别落在对应回环
> 上，周期与收敛条件均不同。

## A2 — Future Trigger ★

1. **情境**：给AI项目设计迭代机制；复盘"改了但没用"；区分什么问题该多快修；
   建立上线后的持续优化节奏。
2. **语言信号**："怎么建立反馈循环" / "迭代机制" / "问题修正流程" / "运营反馈"
   / "持续改进" / "feedback loop" / "iteration cadence" / "AI运维"。
3. **相邻区分**：与 fde-pilot-execution 不同——那张卡是主执行流程（含回环触发
   点），本卡专讲**三类回环的设计与区分**；与 fde-risk-human-fallback 不同——
   兜底保当下不断业务，回环让系统事后变好。

## E — Execution (可执行步骤)

**输入契约**：项目所处时期（构建/试点/运营）与要处理的问题清单。

1. **时期判定**：在建→问题修正；试点中→优化迭代；已上线→运营反馈。
2. **按时期配置回环**：
   - 问题修正：缺陷登记→修复→验证→关闭（周期≤周）；
   - 优化迭代：试点复盘（指标+采纳双维）→改进假设→改动→再试点（以闸门通过收敛）；
   - 运营反馈：固定节奏（月度）反馈会→改进 backlog→排期→上线→效果追踪（不收敛，持续）。
3. **错配自检**：当前问题是否用了对应时期的回环？（用工程回环应付业务问题 =
   错配，升级回环级别。）
4. **输出契约**：回环配置表（时期/输入源/周期/收敛条件/参与角色）+ 当前问题
   的回环归属判定。

## B — Boundary (边界)

- **不要**用于：与AI系统无关的一般项目管理迭代；把回环当挡箭牌（没有收敛条件
  的无限迭代=不作为）。
- **失败模式**：三类回环混用（见上）；优化迭代无收敛条件（试点永远"再试一轮"）；
  运营反馈只收集不闭环（听了不改）。
- **作者盲点**：图未给各回环的节奏与收敛条件，本卡按工程实践补全（E段标注为
  约定）。
